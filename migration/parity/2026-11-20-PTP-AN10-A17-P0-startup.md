## 设计与配对口径

- **分组（blocked）配对**：E6 的 runner 每个 iteration 内按 `E6-0 → E6-1 → E6-2 → E6-3` 连续跑完 4 个变体，
  再进入下一 iteration。同一 iteration 的四条记录落在同一设备状态窗口内（块内跨度约 50–65 s），
  因此配对键是 `iteration`，不是跨批次相减。
- **变体**：`E6-0` 隔离最小配置基线（等价 E3-0）／`E6-1` `+ --preserve-symlinks`／
  `E6-2` `+ --import startup-fs-cache-shim.mjs`／`E6-3` 两者叠加。
- **终点**：4 个变体同为 `web`，统一用 `httpReadyMs`（首次 HTTP 状态）配对；`spawnMs` 四个变体都是 48–50 ms，
  配对时排除，避免把进程启动抖动算进优化收益。
- **统计口径**：均值、样本标准差（n−1）、中位数、nearest-rank P95、配对差值的 95% 置信区间
  （t 分布，df=9，t₀.₉₇₅=2.262）、Cohen's dz（配对差值均值 / 差值标准差）、
  符号检验双侧精确 p（n=10 时最小可达 0.00195）。差值定义为「后者 − 前者」，**负数＝更快**。
- 官方摘要（`E6.summary.md`）按 `durationMs` 报 P50/P95；本报告按 `httpReadyMs` 报，两者相差约 10–15 ms（`spawnMs`），
  不影响任何配对方向，下表不混用两列。

## 结论（只陈述配对数据）

1. **两项 P0 候选优化在隔离最小配置下都成立**：`--preserve-symlinks` 单独 **−2655 ms（−15.5%）**，
   只读 FS 缓存垫片单独 **−1794 ms（−10.5%）**，两者叠加 **−4666 ms（−27.2%）**；
   三组配对都是 10/10 块更快，符号检验 p=0.00195（n=10 的下限），dz 分别为 −3.51 / −2.12 / −6.12。
2. **叠加近似可加，不能声称协同**：两项独立收益相加为 −4449 ms，实测叠加为 −4666 ms，多出 217 ms（约 1.3%），
   远小于组间波动；只能说「没有明显负交互，接近相加」。
3. **单独比较**：E6-1 比 E6-2 还快 862 ms（9/10 块），即「跳过 realpath」的收益大于「缓存元数据」的收益；
   这与 11-19 的 E5 profile 一致（`finalizeResolution→realpathSync` 1.62 s + `canonicalPath` 1.17 s ≈ 2.79 s，
   对 E6-1 的 2.66 s；E5 的 stat/realpath 总额 8.6 s，垫片只覆盖其中落在两个只读前缀上的部分）。
4. **绝对量不是生产数字**：E6-3 均值 12.48 s、基线 17.14 s；这是**隔离空配置**。生产配置在 11-18 的 E3-P 上比 E3-0
   多约 0.8 s，模块图更大，所以生产上的绝对收益应≥本值，但在 T1 复测前不得写成「生产冷启动已到 12.5 s」。
5. **本轮 E6 不覆盖宿主侧 P0**：`DshHost` 的 300 ms 死等改成「等首行 marker（300 ms 上限）」、启动期探针
   150 ms（前 20 s）这两项**已在生产代码里**，但 E6 走的是诊断 runner，不经过 `DshHost`，所以本报告对它们没有数据。

## 限制（如实记录）

1. **块内顺序固定**：每个 iteration 都先 E6-0 再 E6-1/E6-2/E6-3。漂移斜率与前后半程差都不支持「后跑者系统性占便宜」，
   但只有随机化块内顺序的重复实验才能把位置效应彻底分离；当前结论应表述为「固定顺序、10 个块同向」。
2. **单设备、单日、单批次**：温度/电量/充电状态未记录（与 11-17、11-18 记录相同）。同日 E6-0（17.14 s）比 11-19 E5 的
   同构 E3-0（16.06 s）慢约 1.1 s，再次说明**跨批次绝对值不可比**，本报告只做同批次配对。
3. **本轮没有 CPU profile**：机制归因借用 11-19 的 10 份 E5 profile，是本轮的**推断**，不是本轮 syscall 计数。
   要证明热点确实消失，需要在 E6-3 上重取 profile 对比自时间。
4. **`httpReadyMs` ≠ 可交互**：探针约 100 ms 轮询，对四个变体同向，不改变差值方向，但绝对值有 ±100 ms 量化误差。
5. **HTTP 状态分布不同**：E6-0 有 1 次 401，E6-3 有 3 次 401（受保护路由先响应），其余均为 404；响应体并非同一条路由。
   剔除 401 块后 E6-3 均值 12.45 s、E6-0 均值 16.97 s（−4.52 s），方向与量级不变。
6. **两个开关都还没进生产 argv**：`ProotCommandBuilder` 仍只加 `--import link-shim.mjs`；
   `startup-fs-cache-shim.mjs` 只是被 provision 到 guest 缓存目录、由 E6 变体显式 `--import`。
   因此本记录**不能**宣称「P0 已让生产启动变快」，只能宣称「候选开关的配对收益成立，可进入采纳评估」。
7. **`--preserve-symlinks` 改变模块解析语义**（保留 symlink 路径、模块身份不再统一到 realpath）。本记录只测耗时与
   HTTP 就绪，没有验证 Cordis 插件 manifest 扫描、`ui_*` 与单例包双实例化；那是采纳前必须单独过的门。
8. **compile cache 仍 not-evaluable**：本轮未启用，也未触碰；E4 的结论不变。

## 下一步

1. **T1 生产配对（G6）**：同一构建、同一设备，用 `startup-perf` 采 `bridge.complete` ≥10 次，与同批次 T0 配对；
   这是唯一能对「生产启动是否变快」下结论的格子，也是宿主侧 300 ms / 探针改动的唯一验收口。
2. **生产配置下复测**：在 E6 的基线上改用生产 profile（或直接做 T1 A/B），确认 −4.7 s 的相对收益在更大模块图上是放大还是摊薄。
3. **采纳前语义验证**：`--preserve-symlinks` 跑 Cordis 插件加载 / `ui_*` / 单例包专项；垫片确认 45 s TTL、只读前缀、
   与 `link-shim.mjs` 的加载顺序，以及层版本变化后的缓存失效。
4. **机制闭环**：在 E6-3 上重取 CPU profile，确认 `finalizeResolution→realpathSync` 与 `internalModuleStat` 自时间下降。
